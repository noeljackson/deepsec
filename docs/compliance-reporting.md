# Compliance-formatted reports

`deepsec report` can emit a structured, audit-ready JSON document
suitable for SOC 2, ISO 27001, FedRAMP, or NIST SSDF evidence
gathering. The format carries the provenance an auditor cares about:
which binary produced the finding, what matcher pack and prompt pack
it ran against, what model gave the verdict, and an HMAC over the
report so tampering is detectable.

## Generating a report

```bash
# Default trio (markdown + JSON + CSV) — unchanged from prior behaviour
deepsec report --project-id myproj

# Compliance-formatted JSON (SOC 2 framing)
deepsec report --project-id myproj --format soc2 --output report.json

# Same shape, SSDF framing — downstream tooling can branch on the
# `format` field
deepsec report --project-id myproj --format ssdf
```

If `--output` is omitted, the report writes to
`data/<projectId>/reports/compliance.<format>.json`.

The SOC 2 and SSDF formats currently share an identical schema; the
`format` field is recorded verbatim so downstream tooling can switch on
it. Future revisions may diverge while keeping the schema version
stable.

## Signing and verification

Set `DEEPSEC_REPORT_SIGNING_KEY` in the environment when generating a
report. The CLI computes an HMAC-SHA256 over the canonical-JSON
encoding of the report (with the signature block elided) and stores it
inside the report's `signature` field. The key itself is never written
to disk.

```bash
export DEEPSEC_REPORT_SIGNING_KEY="rotate-this-secret"
deepsec report --project-id myproj --format soc2 --output evidence.json
```

To verify:

```bash
export DEEPSEC_REPORT_SIGNING_KEY="rotate-this-secret"
deepsec report --verify evidence.json
```

The verifier prints a warning if the report was produced by a binary
whose matcher pack or prompt pack hash differs from the current
binary's — useful for catching "this report was generated by an old
build" without failing verification.

The `key_hint` field in the signature is the first 16 hex chars of
`SHA-256(key)`. Multiple key versions can coexist: the verifier can
pick the right one based on the hint without needing the full key
stored alongside the report.

## Schema

```json
{
  "schema_version": "1.0",
  "format": "soc2",
  "generated_at": "2026-05-13T12:00:00Z",
  "project_id": "myproj",
  "manifest": {
    "scanner_version": "<git SHA at build time>",
    "build_date": "2026-05-13T11:00:00Z",
    "matcher_pack_hash": "<SHA-256 of the embedded matcher TOMLs>",
    "prompt_pack_hash": "<SHA-256 of the embedded prompts>",
    "providers": ["anthropic", "openai"],
    "models": ["claude-sonnet-4-6", "gpt-4.1-mini"],
    "total_cost_usd": 0.42,
    "total_run_count": 12,
    "findings_count": 18
  },
  "findings": [
    {
      "finding_id": "<deterministic 16-hex id, stable across re-scans>",
      "detected_at": "2026-05-12T16:32:00Z",
      "detected_by_run": "20260512163200-aaaa",
      "provider": "anthropic",
      "model": "claude-sonnet-4-6",
      "severity": "HIGH",
      "cwe": "CWE-918",
      "vuln_slug": "ssrf",
      "file": "src/lib/fetch-proxy.ts",
      "lines": [12, 13],
      "title": "User-controlled URL fetched server-side",
      "description": "...",
      "recommendation": "...",
      "confidence": "high",
      "status": "open",
      "status_changed_at": "",
      "evidence_hash": "<SHA-256 binding file content, slug, lines, run>"
    }
  ],
  "signature": {
    "algorithm": "HMAC-SHA256",
    "key_hint": "<first 16 hex chars of SHA-256(key)>",
    "value": "<64 hex chars>"
  }
}
```

### Status values

- `open` — still considered exploitable (revalidation either absent or
  `true-positive`).
- `false-positive` — revalidation marked the finding as not exploitable.
- `verified-fix` — revalidation confirmed the code has been fixed.
- `uncertain` — revalidation couldn't determine the verdict.

### `evidence_hash` semantics

The `evidence_hash` is `SHA-256(file_path || file_hash || vuln_slug ||
produced_by_run || line_numbers)`. It binds the finding to the file's
content at scan time. An auditor checks: if a later scan of the same
file produces the same `FileHash`, the evidence still corresponds to
the same source. If the file changes, the next scan will produce
different `evidence_hash` values and the auditor can see the diff
between report versions.

### `finding_id` semantics

The `finding_id` is `SHA-256(file_path || vuln_slug || line_numbers)`
truncated to 16 hex characters. It is **deterministic across
re-scans**: the same code, the same matcher, the same lines produces
the same id. This makes it usable as a key in downstream GRC tooling
without needing custom remapping.

## What's deliberately not in scope

- **Integration with specific GRC platforms** (Vanta, Drata,
  ServiceNow GRC). The JSON is the building block; integrations live
  outside the scanner.
- **Patch-validation evidence**. Tracked in the patch-generation
  issue (#47). When that lands, the compliance report will gain a
  `verified_fix` sub-record per finding linking to the validating
  commit.
- **Multi-project rollup**. One project at a time today; aggregate
  across projects in a downstream pipeline.

## Versioning

The `schema_version` field is the contract. Adding new optional fields
to existing objects is a non-breaking change; renames, removals, or
type changes bump the major. Downstream tooling should branch on
`schema_version` if it needs to support multiple deepsec generations.
